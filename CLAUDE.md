# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Xuewen (學問) is a self-hosted reference manager for CS research papers: a single Rust binary that is both a CLI and an Axum web server, with a Svelte 5 SPA embedded into the binary.

## Dev environment

This is a Nix flake. Enter the dev shell with `nix develop` (or `direnv allow` — there's a `use flake` `.envrc`). Treat the shell as already active when `$IN_NIX_SHELL`/`$DIRENV_DIR` is set; otherwise wrap commands in `nix develop -c '<cmd>'`. The shell provides `cargo/rustc/clippy/rustfmt`, `poppler-utils` (`pdftotext`), `sqlite`, and `nodejs`.

## Common commands

```sh
# Frontend must be built before the embedded web UI works (see Architecture).
npm --prefix frontend install          # once
npm --prefix frontend run build        # build the SPA into frontend/dist
npm --prefix agent-runner install      # once, only needed for Agent Ask ([ai.agent.*])

cargo run -- serve                     # web UI at http://127.0.0.1:8080 (loopback; --allow-remote to bind publicly)
nix build                              # ./result/bin/xuewen with the frontend baked in

cargo run -p xuewen-desktop            # macOS desktop app (dev; opens a window)

# Frontend hot-reload dev: run both; Vite (:5173) proxies /api and /papers to the backend (:8080).
cargo run -- serve
npm --prefix frontend run dev
```

Tests & checks:

```sh
cargo test                             # backend unit + integration tests
cargo test -p xuewen-desktop           # desktop crate unit tests (needs sidecar files — see note below)
cargo test <name_substring>            # a single backend test
cargo clippy                           # lint
cargo fmt

# Frontend tests MUST run from frontend/ — a bare `npx vitest` at the repo root mis-resolves.
npm --prefix frontend test             # vitest run (whole suite)
cd frontend && npx vitest run src/lib/foo.test.ts   # a single frontend test file
npm --prefix frontend run check        # svelte-check (TypeScript)
npm --prefix agent-runner test         # agent runner protocol tests (node --test)

nix flake check                        # builds packages + checks (a NixOS VM test on Linux)
```

Semantic search and the daily feed need a running **Qdrant** (`http://localhost:6333`) plus `[ai.embedding]` configured; keyword search, chat, and everything else do not.

Desktop crate builds (`cargo build`/`test -p xuewen-desktop`) link against macOS system frameworks (WebKit, AppKit) through Tauri; if that fails inside the Nix shell, fall back to running the same command outside it (plain `cargo`, via a rustup toolchain) rather than fighting the sandboxed linker. They also require `desktop/binaries/pdftotext-<host triple>` and `node-<host triple>` to exist: `tauri-build` validates the `externalBin` paths at compile time, even for tests, so on a clean checkout (that directory is gitignored) the build fails with `resource path binaries/pdftotext-aarch64-apple-darwin doesn't exist`. Run `bash desktop/scripts/prepare-sidecars.sh` to create them properly, or — as a quick local unblock — copy any `pdftotext`/`node` executables to those paths (only their existence matters for compiling). To produce the `.dmg`: `prepare-sidecars.sh` (bundles Node + `pdftotext` as sidecars; needs Homebrew `poppler` and `dylibbundler`), then `cd desktop && npx @tauri-apps/cli build`.

## Architecture

**Workspace: server crate + desktop crate.** The repo is a Cargo workspace (`[workspace] members = [".", "desktop"]`): the root `xuewen` crate is the CLI/server; `desktop/` (`xuewen-desktop`) is a Tauri v2 crate that boots the *same* Axum stack in-process — `xuewen::server::spawn_services` builds every service from a `Config`, then `xuewen::server::serve_on`/`web::serve_on` serve them on a listener the desktop crate binds itself (`127.0.0.1:0`, so it never collides with a `cargo run -- serve` on `:8080`) — and opens a webview at that address instead of mounting routes for a terminal user to hit. Bundled `pdftotext`/`node` sidecars are found by prepending their directory (`Contents/MacOS` inside the `.app`) onto `PATH` before the backend starts, so `src/pdf.rs` and `src/agent`'s plain `Command::new("pdftotext"/"node")` resolve them without any desktop-specific code path. Desktop config bootstraps into `~/Library/Application Support/Xuewen/` on first launch (`desktop/src/bootstrap.rs`) and is otherwise the same `xuewen.toml` the server reads.

**Single binary, embedded SPA.** `src/main.rs` is the CLI; `serve` starts the web server. The Svelte frontend is built to `frontend/dist` and embedded via `rust-embed` (`src/web/assets.rs`). `build.rs` writes a placeholder `index.html` when `frontend/dist` is missing so `cargo build`/tests work without a frontend build. In **debug** builds `rust-embed` reads `frontend/dist` from disk at request time — a frontend rebuild is served live with no Rust recompile; **release** (`nix build`) bakes it in.

`static_handler` is more than a byte pump, because the reader tier is ~5.8 MB (PDFium wasm 4.6 MB + worker-engine + viewer chunks) and it used to be re-fetched in full on every page load. It now sets, per path class: `Cache-Control: immutable` for Vite's fingerprinted `assets/*` (their names change with their bytes, so they are fetched once per build) and `public, no-cache` for stable URLs like `index.html`, whose **weak** ETag — weak because the same resource ships identity/gzip/br — answers `If-None-Match` with a bodiless 304. Bodies are gzip/br compressed with the result **cached in-process keyed by content hash** (`COMPRESSED`): compressing the wasm costs ~500 ms while the loopback transfer it saves costs ~40 ms, so per-request compression would be a net loss locally and only pay off remotely, whereas compressing once wins both ways. Keying on the hash is what preserves the debug live-reload above — a rebuilt asset hashes differently and misses the cache instead of being served stale. `Cargo.toml` also pins `opt-level = 3` on `sha2`/`flate2`/`brotli` in the dev profile: unoptimized, rust-embed's per-request SHA-256 alone measured 38-44 ms for the wasm (~119 MB/s), which dominated every dev request.

**Config (`src/config.rs`).** One `xuewen.toml` (`--config` to override; `xuewen.example.toml` is the documented template). Only three keys are required: `inbox_dir`, `library_root`, `database_url`. All LLM/AI settings live under **`[ai]`** (shared `base_url`/`api_key_env`/`model`); each use — `[ai.embedding]`, `[ai.summary]`, `[ai.daily]`, `[ai.citations]`, `[ai.translate]` — is `#[serde(flatten)]`-ed and overrides only what differs (`AiConfig::resolve`). The reader's Ask tab / paper chat is powered separately by `[ai.agent.*]` (`AgentConfig`, not an `AiDefaults` flatten) — there is no `[ai.chat]` section. API keys come from the environment via `api_key_env` (default `OPENAI_API_KEY`), never the file. A feature is **off unless its section is present**.

**Storage & search.** SQLite via SQLx (`src/db.rs`); `migrations/` run automatically on startup (`sqlx::migrate!`). Keyword search is Tantivy (always on); semantic search is Qdrant (optional). `SearchService` (`src/search/`) fuses BM25 + vector hits into one ranked list; the embedder + Qdrant store are built from `[ai.embedding]` + `[search]`. Search accepts GitHub-style qualifiers parsed canonically in `src/search/query.rs` (mirrored for UI sync in `frontend/src/lib/searchQuery.ts` — the two share fixture cases, change both together): `tag:` `project:` `is:starred` `status:` `in:title|authors|abstract|body|notes` `author:` plus quoted phrases; the web UI's search-box string is the single source of truth for all list filters (pills and popover toggles edit it, `state.svelte.ts` caches its parse on `filters`).

**Ingest pipeline (`src/pipeline.rs`).** PDF → `pdftotext` extraction (`src/pdf.rs`) → metadata resolution (`src/resolve/`: arXiv, Crossref, DBLP, Unpaywall OA, GROBID header fallback) → dedupe + deterministic cite key (`src/matching.rs`, `src/naming.rs`) → filed under `library_root` → indexed into Tantivy + Qdrant. `ingest` takes a local PDF; `import` fetches one first (arXiv direct → EZproxy proxy → Unpaywall OA, see `src/import.rs`); `watch` auto-ingests the inbox.

**Services (wired in `serve`).** `SearchService`, `DailyService` (ranked daily arXiv recs), `SummaryService` (per-paper LLM summaries), `CitationsService` (per-paper reference parsing), and `TranslateService` (LLM/DeepL selection translation; `POST /api/translate`) are each built `from_config` and disabled when their config is absent. `AgentService` (`src/agent/`) powers the per-paper Ask tab: each turn spawns `node agent-runner/src/runner.mjs` (Claude Code / Codex SDKs) over a read-only workspace `<library_root>/agent/<paper_id>/` (`paper.txt` + optional `repo/` shallow clone; attach via `PUT /api/papers/{id}/code` or `xuewen code set`) — "read-only" bounds writes/exec/network, not reads: neither backend's sandbox is path-scoped, so it can read any file on disk the server process's user can read (see README's "Sandbox boundary, honestly"). Gated by `[ai.agent.claude_code]` / `[ai.agent.codex]`; needs Node ≥ 20 and `npm --prefix agent-runner install`. `web::serve` (`src/web/`: `mod.rs` routes, `api.rs`, `chat.rs`, `dto.rs`, `assets.rs`) mounts the Axum routes plus the SPA. The web UI has **no auth** — mutating endpoints are loopback-only unless `--allow-remote`.

**Organization: projects, tags, star.** Always on (plain SQLite CRUD in `src/db.rs`, no `[ai.*]` gate) — not a `from_config` service. Projects are named groups of papers (many-to-many via a join table); a project carries only a name (and paper count) — it no longer has a `note` field (dropped in migration `0016_drop_project_note.sql`). Tags are free-form labels, also many-to-many, support `/`-nested names (e.g. `nlp/eval`), and are garbage-collected when their last paper reference is removed. Star is a plain boolean flag on the paper row. All three are exposed both from the CLI (`project`, `tag`, `star`/`unstar`) and from the web UI's `FilterRow.svelte` pill bar (filter, create, and — Task 14 — a hover "⋯" menu per pill for rename/delete).

**Annotations (`src/annotations/`).** Reader marks — highlight, underline, strikeout, squiggly, sticky note — stored as a **SQLite sidecar** (`0020_add_annotations.sql`), never written into the PDF. That is the whole design constraint: `papers.content_hash` has to stay true of the bytes on disk, since it drives ingest dedupe and the `_unsorted/<hash>.pdf` name, so the annotation plugin runs with `autoCommit: false` and the library file is never touched. Always on (no `[ai.*]` gate), like projects/tags/star. Each row is **hybrid**: typed projection columns the backend can query (`page_index`, `kind`, `color`, `quoted_text`, `note`) plus an opaque `payload` holding the plugin's own transfer item verbatim, so a field this app has never heard of survives the round trip; an unparseable payload degrades to `NULL` and the row still lists rather than being lost. The id is minted by the reader, which is why the write is `PUT /api/papers/{paper_id}/annotations/{annotation_id}` (idempotent on retry) alongside `PATCH`/`DELETE` there and `GET`/`DELETE` on the collection. `note` text is indexed into Tantivy (`in:notes`) through a `notes_hash` stamp on `search_index`, so editing a note reindexes the doc from the stored chunks without re-running `pdftotext` (`src/search/planner.rs`). CLI: `xuewen annotation list|rm|clear`.

**CLI subcommands** (all in `src/main.rs`): `serve`, `ingest`, `import`, `watch`, `identify` (`--doi`/`--arxiv`/`--title`), `refresh`, `search`, `export` (BibTeX/BibLaTeX), `project`, `tag`, `star`, `unstar`, `annotation` (`list`/`rm`/`clear`), `index` (`status`/`rebuild`), `summarize`, `code` (`set`/`status`/`rm` — attach/inspect/detach a paper's code repo for Agent Ask), `delete`/`restore`/`purge`, `proxy-cookie`.

**Frontend (`frontend/`).** Svelte 5 (runes) + Vite + Tailwind v4 + Vitest/@testing-library. Reactive app state is in `src/lib/state.svelte.ts` (`$state` stores for tabs/viewer, theme, selection, UI). `src/lib/api.ts` is the fetch client; `src/lib/shortcuts.ts` is the window-level single-key keymap.

## PDF viewer (EmbedPDF) gotchas

The reader is hand-rolled from EmbedPDF's primitives (not the ready-made `@embedpdf/svelte-pdf-viewer`). Engine/plugin config is centralized in `src/lib/pdfEngine.ts` (`ENGINE_OPTIONS`, `viewerPlugins()`); `PdfViewer.svelte` renders one persistent `PdfTab.svelte`/`PdfDeck.svelte`/`PdfPages.svelte` per open tab. Several settings are load-bearing and documented inline — don't strip them:

- Page rendering is layered (`PdfPages.svelte`'s `renderPage` snippet): `RenderLayer` with **`scale={1}`** (a cheap base rendered once, CSS-scaled to fit) plus `TilingLayer` (crisp tiles for the visible area only, drawn at the real zoom). Removing `scale={1}` reverts to full-page re-renders on every zoom tick — the exact perf bug this layering fixed.
- `worker: true` — PDFium runs in EmbedPDF's stock **blob module worker**, not the main thread (an earlier attempt at `worker:true` hung on "Loading document…"; that was diagnosed and fixed on 2026-07-13, not a dead end — see the two points below). Two things had to be fixed to get there:
  - `wasmUrl: new URL('/pdfium.wasm', location.origin).href` — must be a **fully-qualified URL**, not a bare path. The blob worker's own `self.location` is itself a `blob:` URL, which has no hierarchical path to resolve `'/pdfium.wasm'` against — Chromium throws `Failed to parse URL from /pdfium.wasm` *inside the worker*, with no network entry and no error surfaced to the main thread, so the symptom is just an indefinite "Loading document…". A fully-qualified URL needs no base-relative resolution, so it works regardless of the worker's own location. The wasm is still **self-hosted** — the default is a jsDelivr CDN, which breaks offline — but it is now imported as `@embedpdf/pdfium/pdfium.wasm?url` (a subpath the package exports explicitly), so Vite emits it fingerprinted under `assets/` and the backend can serve it `immutable`; it is no longer copied into `frontend/public/` by a `copy-wasm` prehook, and that script is gone. Vite hands back a path, which `new URL(..., location.origin)` still makes absolute — the blob-worker requirement above is unchanged, so **keep that `new URL` wrapper**. `fontFallback: null` (no external font fetches) still applies.
  - Any `PdfDocumentObject`/`PdfPageObject` your own code reads off EmbedPDF's Svelte bindings (e.g. `useDocumentState()`) is a **reactive Svelte `$state` proxy**. Handing one back into an engine call (e.g. `getPageAnnotations(doc, page)`) round-trips it through `postMessage` to the worker, and a live proxy throws `DataCloneError: ... could not be cloned`. Call `$state.snapshot(doc)` once before passing document/page objects into any engine call that might run in worker mode — see `PdfPages.svelte`'s citation-extraction effect.
- Citation extraction (that same effect) is scheduled with `runWhenIdle` (`src/lib/idle.ts`, a `requestIdleCallback` wrapper) rather than firing on first paint — PDFium calls are expensive even off the main thread (the worker round-trip still has to happen before first pages paint). The effect deliberately has **no cleanup on re-run**, only on `onDestroy`: an earlier bug had the initial FitWidth zoom re-firing this effect and cancelling a pending extraction before it ever finished; a one-shot `extractedFor`/`extractionCancelled` guard replaced the cleanup instead.
- Citation popovers show structured references (title/authors/venue/year): the frontend POSTs raw reference text to `/api/papers/{id}/citations` (`src/citations/`), which parses the big-4 CS styles by pattern matching (`src/citations/heuristic.rs`: style vote across entries, venue publisher-family tie-break, strict per-entry validation) and — when `[ai.citations]` is configured — sends only the leftover entries to the LLM; results are cached in SQLite so repeat opens of the same paper don't re-parse. The endpoint is always available; without `[ai.citations]` unparseable entries stay null and their popovers show the raw extracted text. PDFs with no hyperlinked citation annotations fall back further, to text-layer marker detection (`textCitations.ts`, numbered- and author-year-style segmentation in `citations.ts`).
- The annotation plugin is registered with **`autoCommit: false`** (`ANNOTATION_OPTIONS` in `pdfEngine.ts`) — see the Annotations paragraph above for why the PDF must never be written. Consequences to keep in mind when touching that code:
  - **Never hand `useAnnotation` a document the plugin has not seen.** It is called at the top of `PdfPages.svelte`, which mounts as soon as its tab exists — long before `PdfDeck`'s `openDocumentUrl` resolves — while the plugin only creates a document's annotation state in `onDocumentLoadingStarted`. The hook's own effect calls `scope.getState()` eagerly, and that *throws* on an unknown id; the throw lands inside Svelte's effect flush, aborts the remaining effects, and leaves the whole reader permanently blank with no page ever rendering (the only clue is one `Annotation state not found for document: <id>` per open tab). Hence the id is withheld — `useAnnotation(() => (docState.current?.document ? documentId : ''))` — which takes the hook's own early-return path until the document is ready.
  - **Ownership, not "everything the plugin knows about."** A PDF can arrive with marks already in it, and the plugin surfaces those exactly like ours. `annotationSync.ts` persists only ids it imported from the sidecar or saw created this session (subtype-whitelisted); adopting a foreign mark would copy it into the sidecar and then import it *on top of* the original on the next open, drawing it twice.
  - Writes for one mark are **chained per id**, and each queued step reads the plugin and the cache when it runs rather than when it was queued. Undo/redo turns a create into a delete and back within a click, and an eagerly-computed save behind an in-flight DELETE would see the row it was about to remove, call the mark unchanged, and skip the write.
  - The link "renderer" registered in `annotationRenderers.ts` matches nothing on purpose: it replaces the plugin's own link renderer by id, so link annotations stay invisible to it and the reader's `CitationLayer` keeps owning citation clicks.
  - Export (`annotationExport.ts`) opens a **second, throwaway document** from the same URL, replays the rows into that one, commits *there*, and `engine.saveAsCopy`s it. It waits for the plugin's `loaded` event before committing (imports are queued until a document's own annotations have been read) and closes the throwaway in a `finally`, or a failed export leaks a PDFium handle and a slot against `maxDocuments`.
  - Undo/redo is the optional `@embedpdf/plugin-history`, scoped to the annotation plugin's private `'annotations'` topic (mirrored as `ANNOTATION_HISTORY_TOPIC`, version-pinned to 2.14.4). `canUndo`/`canRedo` are method calls, not reactive state — `AnnotationHistory.svelte` mirrors them into runes off `onHistoryChange`.
- **Copying selected text is entirely this app's job** (`src/lib/pdfCopy.ts`). EmbedPDF binds no keys at all, and the only `navigator.clipboard` write in the package tree lives in an auto-mounted `CopyToClipboard` utility that ships with the plugin's `/svelte` subpath — deliberately **not** registered here (it writes bare, with no `execCommand` fallback, so it is dead over plain-HTTP `--allow-remote`; `pdfEngine.ts` keeps the base `SelectionPluginPackage` and says so inline). The browser cannot do it either: a page is an `<img>` and the selection overlay is empty `pointer-events:none` `<div>`s, so the document selection over a page is always collapsed, the copy command stays disabled and **no `copy` event is ever dispatched** — there is nothing to intercept, and `shortcuts.ts` has to handle ⌘C outright. Three things are load-bearing: (1) the text is fetched **eagerly** when a selection settles and cached, because `getSelectedText` is a PDFium worker round-trip and a clipboard write on the far side of one has lost the user gesture that authorized it (WebKit enforces this strictly) — `copySelection()` writes with no `await` in front of it, and a unit test pins that; (2) the trigger is a **trailing debounce on `onSelectionChange`**, not `onEndSelection` alone — the plugin registers its text handler per page with `dragStarted` in that page's closure, so `onEnd` fires only when the pointer is released over the page the drag *began* on, and releasing in the gutter, past the margin, over the toolbar or on a second page (i.e. most multi-page drags) leaves a live selection and no end event; (3) it lives in `PdfDeck` (mounted once) not `PdfPages` (one per open tab), since the selection capability is registry-wide. The Viewport carries `select-none` so the browser's own drag-selection can't grab the floating toolbar's labels mid-drag and make the ⌘C guard stand aside. `REGISTRY_CONFIG` in `pdfEngine.ts` overrides the PDF `CopyContents` permission — one choke point that also gates selection-translate and the annotation plugin's quoted-text capture — because `pdftotext` has already extracted the whole document at ingest anyway. Unverified in WKWebView: the Tauri shell's default Edit ▸ Copy menu item owns ⌘C, so if the desktop app ever fails to copy, first check whether the keydown reaches JS at all before suspecting the clipboard call.
- Inactive tabs are hidden with `visibility:hidden` (not `display:none`) so the viewer isn't remounted — preserving page/scroll and avoiding a thumbnail re-scroll on tab switch. That also means a hidden tab keeps real layout boxes and genuinely rasterizes its pages, which is why `PdfDeck.svelte` opens the **active** document first and drains the rest one per idle callback (`planOpens` in `pdfDeck.ts`): EmbedPDF runs opens through a concurrency-1 engine lane at CRITICAL priority — above `renderPage`, with no preemption — so opening every restored tab at once put each background tab's parse *ahead* of the visible tab's first pixel. Deferred, not disabled: background tabs still load, so switching to one stays instant.
- Anything measuring reader performance in a browser must confirm the tab is actually **visible** (`document.visibilityState === 'visible'`). In a hidden or occluded window Chrome runs no `requestAnimationFrame`, so the virtualized viewport rasterizes *nothing* while the toolbar still shows a correct page count, and `setTimeout` is throttled to ~1/s. The result looks exactly like a hung renderer — a blank viewer, poll loops that never finish, CDP `Runtime.evaluate` timeouts — and is purely an artifact of the window not being on screen.
- Never call the thumbnail plugin's `scrollToThumb` (@embedpdf/plugin-thumbnail 2.14.4): its `scrollTo$` scoped emitter caches its last emission (`cache` defaults `true`; `refreshPages$` opts out of caching, `scrollTo$` doesn't), and `ThumbnailsPane` re-subscribes its `onScrollTo` effect on every window-state change — i.e. on every manual pane scroll — which replays the cached emission and pins the pane to whatever position was last commanded. Diagnosed live 2026-07-14 with stack traces, after two plausible-but-wrong effect-reactivity fixes. Fix: `PdfSidePanel.svelte` positions the pane on open by writing the pane element's `scrollTop` directly from `plugin.getDocumentState(id).thumbs[page].top - 8` (8 = upstream's own `margin` constant), reaching the pane element via a bound wrapper's `firstElementChild` — both couplings version-pinned to ~2.14.4 and guarded to degrade to "pane stays at top" if either breaks upstream. Registration keeps `{ autoScroll: false, scrollBehavior: 'auto' }`: `autoScroll: false` is the other half of the fix (auto-follow snapped the pane on every page change, fighting manual browsing via trackpad-momentum page changes).

## Deployment

NixOS module (`deploy/nixos/`, `nixosModules.default`), a Home Manager module (`deploy/home-manager/`, `homeManagerModules.default`; per-user `systemd --user` service, Linux only), and an OCI image built with `nix2container` (`deploy/k8s/`). See `README.md` for the container/registry details.

Agent Ask needs its Node runner *and* that runner's `node_modules` at runtime, so — unlike the frontend, which `rust-embed` bakes into the binary — it can't ride along in the `xuewen` derivation. The flake builds it separately (`packages.agent-runner`, a `buildNpmPackage` installing to `$out/lib/xuewen/agent-runner`), and both modules default `settings.ai.agent.runner` to that store path via their `agentRunnerPackage` option, since the backend's own default (`agent-runner/src/runner.mjs`, relative to the working directory) only exists in a dev checkout. Each SDK vendors its CLI as a prebuilt native binary: Codex's are static-pie musl, but Claude Code's is glibc-dynamic, so the package runs `autoPatchelfHook` (with `dontStrip`, or the Bun runtime executes instead of the embedded program) and the modules set `USE_BUILTIN_RIPGREP=0` with a real `ripgrep` on `PATH`. The OCI image bundles none of this. The x86_64-linux VM check enables `[ai.agent.claude_code]` and asserts the startup preflight logs no `agent ask:` warning, which is what keeps that wiring honest.
